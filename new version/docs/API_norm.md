# 智慧外科平台接口与数据变更协作规范

## 1. 目的

本规范用于约束智慧外科平台项目中接口、数据结构、算法输入输出以及医学标签定义的变更流程，减少多人协作中的沟通遗漏、联调阻塞和版本不一致问题。

适用对象包括：

- 前端开发：Vue 3 + Vite + TypeScript
- 后端开发：FastAPI
- 算法研发：Python 算法开发、推理服务封装
- 医学评估与顾问成员
- 项目负责人、产品成员

本规范的目标是：

- 保证前后端、算法、医学评估使用同一套协议和定义
- 保证任何影响他人开发的变更可追踪、可同步、可回溯
- 保证联调期和演示期接口稳定

## 2. 基本原则

项目中的接口与数据协作遵循以下原则：

1. 先约定，再开发
2. 谁提出变更，谁负责说明
3. 谁修改协议，谁负责通知受影响方
4. 先更新文档，再提交代码
5. 联调中的协议原则上保持稳定
6. 重要变更优先兼容过渡，不直接破坏已有调用

## 3. 变更分类

以下变更属于本规范约束范围。

### 3.1 接口变更

包括但不限于：

- 新增接口
- 修改接口路径
- 修改请求方法
- 新增、删除、重命名请求参数
- 新增、删除、重命名返回字段
- 修改返回数据结构
- 修改状态码、错误码、错误信息结构
- 修改鉴权方式、鉴权参数

### 3.2 数据结构变更

包括但不限于：

- 新增、删除、修改数据库表
- 新增、删除、修改字段
- 字段类型变化
- 字段含义变化
- 枚举值变化
- 文件存储规则变化
- 病例、视频、用户、报告等核心实体结构变化

### 3.3 算法输入输出变更

包括但不限于：

- 推理服务输入字段变化
- 推理服务输出 JSON 结构变化
- 检测/分割/流程识别输出字段变化
- 时间戳单位变化
- 坐标格式变化
- 标签编号变化
- 标签命名变化
- 模型版本切换导致的结果含义变化

### 3.4 医学定义变更

包括但不限于：

- 手术流程阶段命名变化
- 器械类别命名变化
- 手术场景分类标准变化
- 医学术语定义变化
- 问答知识边界变化
- 医学标签启用/停用变化

## 4. 变更级别

为了明确处理方式，变更分为三级。

### 4.1 一级变更：重大变更

满足以下任一条件时，视为一级变更：

- 会导致已有调用方式失效
- 会导致前端、后端、算法三方至少两方必须同步改代码
- 会影响历史数据兼容性
- 会影响医学评估标准
- 会影响当前演示版本或发布版本

处理要求：

- 必须提前沟通
- 必须更新文档
- 必须在 PR 中明确标注
- 必须由相关负责人确认后再合并

### 4.2 二级变更：普通协作变更

满足以下情况之一时，视为二级变更：

- 新增不影响旧逻辑的字段
- 新增接口但不影响旧接口
- 新增枚举值但兼容旧逻辑
- 新增算法结果附加字段

处理要求：

- 需要更新文档
- 需要在 PR 中说明
- 需要通知相关调用方

### 4.3 三级变更：内部实现变更

满足以下情况之一时，视为三级变更：

- 不改变接口对外表现
- 不改变数据结构对外定义
- 不改变算法服务输入输出协议
- 仅为性能优化、内部重构、注释与文档优化

处理要求：

- 可直接开发
- 在 PR 中简单说明即可

## 5. 必须提前同步的变更

以下变更不能直接提交代码，必须先同步相关成员：

1. 接口路径变更
2. 请求参数删除或重命名
3. 返回字段删除或重命名
4. 返回结构层级变化
5. 数据库字段删除、类型变化或语义变化
6. 算法推理输出结构变化
7. 标签编号、标签名、标签定义变化
8. 医学评估口径变化
9. 影响演示或对外展示流程的协议变化

## 6. 可直接修改但需在 PR 中说明的变更

以下变更一般可直接开发，但仍需在 PR 中说明：

1. 内部逻辑重构
2. 不影响已有字段的性能优化
3. 新增兼容性字段
4. 新增不影响旧接口的附加接口
5. 文档补充与错误修正

## 7. 角色职责

### 7.1 变更发起人

谁提出变更，谁负责：

- 说明变更内容和原因
- 评估影响范围
- 更新文档
- 通知相关成员
- 在 PR 中写清楚变更点

### 7.2 前端负责人

负责确认：

- 接口字段是否满足页面展示和交互需求
- 字段命名和类型是否稳定
- 兼容方案是否可落地

### 7.3 后端负责人

负责确认：

- 接口协议是否统一
- 数据结构变更是否合理
- 数据库与服务层是否兼容
- 算法服务接入协议是否明确

### 7.4 算法负责人

负责确认：

- 推理输入输出是否稳定
- 返回结果是否结构化
- 模型版本变更是否影响平台联调
- 标签编号与标签定义是否统一

### 7.5 医学评估负责人

负责确认：

- 医学标签命名是否合理
- 阶段划分和分类定义是否符合医学语义
- 结果口径是否满足评估需求

### 7.6 项目负责人

负责确认：

- 重大变更是否符合当前阶段目标
- 是否会影响里程碑、演示、对外汇报
- 是否需要采取兼容过渡方案

## 8. 文档管理要求

所有协议和结构定义，统一通过仓库文档维护。

建议至少维护以下文件：

- `docs/api-design.md`
- `docs/data-schema.md`
- `docs/model-input-output.md`
- `docs/medical-labels.md`

如果项目初期还未拆分完整文档，也至少应保证：

- 接口定义有统一文档
- 数据结构有统一文档
- 算法输入输出有统一文档
- 医学标签有统一文档

## 9. 标准变更流程

### 9.1 提出变更

发起人在团队协作渠道中说明：

- 变更类型
- 变更原因
- 影响范围
- 是否影响联调
- 希望何时生效

### 9.2 更新文档

发起人先修改对应文档，再开发代码。

例如：

- 接口改动更新 `docs/api-design.md`
- 数据结构改动更新 `docs/data-schema.md`
- 算法输出改动更新 `docs/model-input-output.md`
- 医学标签改动更新 `docs/medical-labels.md`

### 9.3 相关方确认

根据变更内容由相关负责人确认。

例如：

- 接口字段变更：前端负责人 + 后端负责人确认
- 算法输出变更：算法负责人 + 后端负责人确认
- 医学标签变更：医学负责人 + 算法负责人确认
- 影响演示流程：项目负责人确认

### 9.4 开发与提 PR

开发完成后，在 PR 中明确：

- 本次是否涉及接口变更
- 本次是否涉及数据结构变更
- 本次是否涉及算法输入输出变更
- 是否需要联调
- 是否存在兼容方案或迁移要求

### 9.5 联调与验证

对一级变更和关键二级变更，合并前建议完成至少一次联调验证。

验证内容包括：

- 前端接口可调用
- 后端字段正确返回
- 算法结果格式正确
- 医学标签解释一致

## 10. 变更通知模板

团队沟通时，统一使用以下模板：

```text
【变更类型】
接口变更 / 数据结构变更 / 算法输出变更 / 医学标签变更

【变更级别】
一级 / 二级 / 三级

【影响模块】
前端 / 后端 / 算法 / 医学评估 / 产品

【变更内容】
请简要描述改了什么

【变更原因】
请说明为什么要改

【兼容方案】
无 / 保留旧字段过渡 / 新旧接口并行 / 其他

【计划生效时间】
例如：本周 develop 合并后生效

【是否需要联调】
是 / 否

【负责人】
填写变更发起人
```

## 11. 兼容性规则

对于已经进入联调阶段的接口和结构，优先采用兼容过渡方案，避免直接破坏已有调用。

### 11.1 推荐做法

- 新增字段优先，不轻易删除旧字段
- 字段重命名时，短期内保留旧字段映射
- 新接口上线后，旧接口保留一个过渡周期
- 模型版本升级时，保持输出结构稳定

### 11.2 不推荐做法

- 直接删除前端仍在使用的字段
- 直接修改字段含义但不通知
- 算法返回结构频繁变化
- 医学标签命名未经统一即直接替换

## 12. 算法服务输出规范要求

算法对平台交付的内容应是稳定协议，而不是临时实验结果。

算法服务至少应明确：

- 输入字段列表
- 输出字段列表
- 字段类型
- 字段含义
- 时间单位
- 坐标单位和格式
- 空结果返回形式
- 失败时返回结构
- 模型版本标识

建议所有算法服务在文档中附带一个最小 JSON 样例。

## 13. 医学标签管理规则

医学标签、器械类别、手术阶段、场景类别等应有唯一真源，不允许各模块各自命名。

建议统一维护在：

- `docs/medical-labels.md`

每个标签建议至少包含：

- 标签编号
- 中文名称
- 英文名称
- 定义说明
- 适用场景
- 是否启用
- 备注

标签规则：

- 标签新增必须经过医学评估负责人确认
- 标签改名必须同步算法、后端、前端
- 标签编号一旦对外使用，原则上不随意更改

## 14. PR 必填要求

凡涉及接口、数据结构、算法输出、医学标签的 PR，必须写明：

1. 变更类别
2. 影响范围
3. 是否破坏兼容性
4. 是否已更新文档
5. 是否需要联调
6. 是否需要数据迁移

未写清楚以上内容的 PR，不建议合并。

## 15. 禁止行为

以下行为在项目协作中原则上禁止：

1. 不更新文档直接修改协议
2. 不通知调用方直接修改字段名
3. 未确认医学定义就修改标签含义
4. 联调阶段频繁修改接口结构
5. 通过口头说明替代正式文档
6. 发现影响他人开发的问题但不主动同步

## 16. 推荐执行规则

项目初期可以先强制执行以下 8 条：

1. 所有协议变更先更新文档
2. 所有一级变更必须提前同步
3. 所有接口字段重命名必须提供兼容方案
4. 算法输出必须提供 JSON 样例
5. 医学标签变更必须经过医学负责人确认
6. PR 必须勾选是否影响接口和数据结构
7. 进入联调后的接口本迭代尽量不再大改
8. 演示版本前禁止随意改核心协议

## 17. 附：常见场景示例

### 示例 1：后端修改返回字段名

原字段：

- `step_name`

拟改为：

- `phase_name`

处理方式：

1. 先在文档中说明字段调整原因
2. 通知前端和算法接入同学
3. 过渡期同时返回 `step_name` 和 `phase_name`
4. 前端切换完成后，再删除旧字段

### 示例 2：算法增加器械检测置信度字段

原输出中无 `confidence`

新增：

- `confidence`

处理方式：

1. 更新算法输入输出文档
2. 通知后端和前端该字段为新增兼容字段
3. 前端可渐进式使用，不影响旧逻辑

### 示例 3：医学顾问调整手术阶段命名

原命名：

- `游离胆囊`

新命名：

- `胆囊游离阶段`

处理方式：

1. 医学负责人确认变更口径
2. 更新标签标准文档
3. 通知算法、后端、前端统一切换
4. 如已进入联调期，应评估是否采用兼容映射过渡
